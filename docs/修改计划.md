# myAIgame v2 执行计划（收敛版）

> 本文档为 v2 的**唯一权威计划**（用户收敛版，2026-08-18）。

## 一、核心目标

本次 v2 不把游戏改造成复杂规则模拟器。

核心原则只有一句：

> **数据库负责把故事记清楚，LLM 负责把故事写好。**

Narrator 是唯一剧情作者。

每回合：

```text
世界状态
+ 当前章节
+ NPC 人物卡
+ 人物关系
+ 重要事件
+ 近期剧情 / 长期记忆
+ 玩家行动
        ↓
      Narrator
        ↓
剧情 Beats
+
[[META]] 状态补丁
        ↓
TURN 落库
        ↓
应用人物 / 关系 / 事件等状态变化
        ↓
异步 Memory / World Tick
```

继续保持：

* 每回合只有 **1 次同步主 LLM 调用**
* SQLite 事件溯源是唯一事实源
* 不做额外模型对同一回合二次裁决
* Memory / World Tick 继续作为异步辅助系统
* 内部人物数据全部对玩家隐藏
* 不建立复杂规则引擎

## 阶段 1：NPC 数据结构重构

### 1.1 NPC 新结构

统一为：

```json
{
  "name": "林雨",
  "age": 19,
  "identity": "学生会成员",

  "status": "右臂受伤，正在和主角一起行动",

  "qualities": {
    "智力": 78,
    "力量": 42,
    "勇气": 63
  },

  "personality": "谨慎、敏感、自尊心强，很少完全相信别人",

  "desire": "保护妹妹并逃离学校",

  "background": "父母长期不在身边，从小承担照顾妹妹的责任",

  "current_thought": "开始怀疑主角隐瞒了一些事情"
}
```

### 1.2 字段职责

#### 基础字段

* `name`
* `age`
* `identity`

原则上稳定。

#### `status`

当前身体、位置、处境等状态。

可以频繁变化。

#### `qualities`

例如：智力 / 力量 / 勇气 / 观察力 / 魅力。不规定固定模板。创建角色时根据角色设定生成合理属性。

变化非常少，只在重伤、长期训练、明显成长、永久身体变化等事件后更新。

#### `personality`

角色长期性格描述。允许 Narrator 修改，但属于**极低频字段**。只有人物经历了足够重大的事件、确实产生人物成长时才能变化。不建立额外人格算法。

#### `desire`

角色当前最重要的愿望、执念或长期目标。允许变化，但属于低频字段。由剧情自然改变。

#### `background`

角色进入当前故事以前的重要经历。原则上不修改。游戏开始以后发生的事情进入事件系统，而不是继续写进 background。

#### `current_thought`

人物此刻最重要的想法、判断或者心理倾向。这是人物连续性的核心字段。可以较频繁变化。

---

### 1.3 删除旧字段

删除：`feeling`、`goal`、`opinion_of_player`、`secret_plan`、`feeling_turn`、`decay_feelings`。

对应逻辑从 `world_state.py`、`npc_mind.py`、`prompts.py`、UI snapshot 中移除。

其中原 `goal` 职责由 `desire` 接替。原 feeling / opinion / secret_plan 的信息统一由 personality / desire / current_thought / status / 关系表 表达。

## 阶段 2：建立有向稀疏关系表

### 2.1 数据结构

人物关系是**有向的**。A 喜欢 B，不代表 B 同样喜欢 A。

```json
{
  "from": "林雨",
  "to": "主角",
  "favor": 32,
  "bond": "目前仍然合作，但已经开始怀疑主角"
}
```

### 2.2 稀疏存储

不创建完整 N × N 矩阵。只有初始存在关系、剧情中产生过有意义互动、对故事有影响的人物之间才创建关系。

### 2.3 favor

范围 0～100。默认没有关系时不创建记录。如果剧情第一次需要建立关系，可以默认 favor = 50。

Narrator 只输出 delta（如 `favor_delta: -6`）。程序负责 clamp 到 0～100。

### 2.4 bond

`bond` 是一句自然语言关系总结。它的重要性高于 favor 数字。Narrator 可以覆盖 bond，使其持续反映当前关系。

## 阶段 3：事件模型扩展

现有 TURN / Event Sourcing 保留，新增最少必要事件。

### 3.1 保留

```text
TURN / NPC_ADD / NPC_STATE / ATTR_CHANGE / ITEM_CHANGE / WORLD_TICK / CRYSTAL / MAIN_PLOT_UPDATE
```

其中旧 NPC_STATE 调整为新 NPC 结构。

### 3.2 新增

- `REL_UPDATE`：`{from, to, favor_delta, bond?, reason?}`
- `QUALITY_UPDATE`：`{entity, changes:{质量:delta}}`（极少出现）
- `IMPORTANT_EVENT`：`{summary, participants, witnessed_by, importance}`
- `PLAYER_UPDATE`：先只承担 `{status: "已死亡"}`
- `CHAPTER`：记录章节开始。
- `CHAPTER_END`：记录章节结束和章节总结。

---

## 阶段 4：Narrator 单作者改造

本次 v2 最核心阶段。

### 4.1 删除 npc_mind

删除 `backend/app/npc_mind.py`；删除 `NPC_MIND_SYSTEM`、`npc_mind_user_message`、`npc_mind.update_minds`、GameSession 中对应异步副作用。

### 4.2 Narrator 输入

每回合获得：世界（设定/规则/时间/地点/暗流）、当前章节（title/time_scope/location_scope/theme/success/failure）、玩家（基础信息/属性/状态/物品）、NPC（姓名/年龄/身份/status/qualities/personality/desire/background/current_thought + witnessed_by/NPC knowledge window）、人物关系（仅注入当前剧情有关：from→to + favor + bond）、重要事件（最近或相关的 IMPORTANT_EVENT）、近期剧情、长期记忆（Memory Engine）。

### 4.3 Narrator 输出

META 扩展为稀疏 patch（choices/minutes/place/present + npc_updates/quality_updates/relationship_updates/important_event/player_update/chapter_done）。所有字段都是稀疏 patch，没有变化就不要输出。

### 4.4 Narrator 状态更新原则

- **status**：有实际处境变化才修改。
- **current_thought**：可以正常变化，但必须由当前剧情和已有事实自然支持。不增加程序级“重要事件才能修改”限制。
- **desire**：低频变化。
- **personality**：极低频变化。
- **qualities**：极低频变化。
- **favor**：普通互动 ±1～±5；明显事件 ±5～±10；极重大事件可以更大，但 Prompt 要求克制。程序只负责最终 0～100 clamp，不自己判断变化是否合理。

---

## 阶段 5：状态补丁落库顺序

必须保持事件因果顺序。Narrator 返回以后：

```text
1. TURN
2. NPC_STATE
3. QUALITY_UPDATE
4. REL_UPDATE
5. IMPORTANT_EVENT
6. PLAYER_UPDATE
```

TURN 是原因，后面的 patch events 是这个 TURN 的结果。

---

## 阶段 6：轻量章节系统

章节只控制故事范围，不做复杂 Director。章节只保证时间范围/地点范围/当前主题；不保证固定剧情、不保证一定成功。Narrator 不限制方法。

玩家成功离开：`chapter_done: {done: true, reason: "主角已经离开学校区域"}` → 章节结束。玩家死亡：游戏失败。

---

## 阶段 7：章节结束与下一章生成

章节结束以后允许额外调用一次**主模型**。这是章节边界调用，不属于普通回合同步预算。

- Chapter Planner 只负责两件事：`chapter_summary` + `next_chapter` 框架。
- **明确禁止 Chapter Planner 修改** personality / desire / current_thought / favor / bond / qualities / NPC status。人物状态只由 Narrative Narrator 修改。
- Chapter Planner 使用**主模型**（下一章讲什么属于核心创作决策）。

---

## 阶段 8：死亡与重开

- 玩家 `player.status = 已死亡` → 本次游戏当前时间线结束。玩家选择「重新开始本章」。
- 实现：章节开始时记录 chapter 起始事件 seq → 删除本章开始以后所有事件 → 重新 build WorldState → 从章节开始状态继续。
- 只支持「本章重开」，不支持任意 TURN 重开 / 多分支保存 / 平行时间线。

---

## 阶段 9：前端调整

- 人物页：玩家（姓名/身份/当前状态，保留现有公开属性/物品可保持现状）；NPC 只显示 姓名/年龄/身份/status。不显示 qualities/favor/bond/personality/desire/隐藏 background/current_thought/任何内部数值。
- 章节 UI：只显示玩家自然应该知道的章节信息（章节名/大致时间/大致地点）；不显示 theme/success_condition/failure_condition。
- 事件树：保留现有；增加 Chapter 分组、IMPORTANT_EVENT 高亮、死亡节点；关系/内心等隐藏状态不得暴露。v2 不增加 pivotal 标记、「影响深远的选择」提示、任意节点重开、多时间线。

---

## 阶段 10：保留现有异步系统

- Memory Engine：继续保留。结晶输入可以包含 TURN / IMPORTANT_EVENT / WORLD_TICK。长期记忆重点记录人物经历、重要关系变化、承诺、冲突、已完成事件、未解决问题、世界事实。
- World Reactor：继续保留。负责玩家不在场期间世界变化、离屏 NPC 行动、世界暗流推进。它不应该成为主要人物关系作者；如需修改离屏 NPC，优先更新 status/current_thought/desire；关系的大幅改变应尽量通过实际剧情表达。

---

## 阶段 11：测试

- 数据层：新 NPC card rebuild、patch、QUALITY_UPDATE、有向 REL_UPDATE、favor clamp、IMPORTANT_EVENT、CHAPTER/CHAPTER_END、PLAYER_UPDATE、本章 rollback。
- META：缺字段安全默认、npc_updates 限制、relationship_updates、quality_updates、important_event、player death、chapter_done、malformed JSON fallback。
- E2E mock 至少三条路径：正常剧情、人物连续性（多回合 rebuild 一致）、死亡（→时间线停止→本章重开→state 回到章节开始）。

---

## 阶段 12：实际长剧情测试

代码全部通过以后先实际跑长局：至少 3 个不同世界、每个 30～50 回合、至少跨 2～3 章。重点观察：人物一致性、人物成长、关系连续性（无漂移）、章节节奏、LLM 状态 patch 质量。

**只有实际出现稳定问题以后，再增加规则。**

---

## 明确不做

多 NPC Agent、独立 Director、NPC 风险评分、betrayal rule、人格 evidence 系统、stress/trust/fear 等大量内部数值、章末人格重写、章末关系重锚、第二模型重新判断人物、pivotal choice、「影响深远的选择」UI、Recap 系统、任意节点 rebranch、多分支保存、战斗判定系统、复杂章节 phase、规则层剧情判定、自动剧情审计员。

如果未来实际测试证明 LLM 无法稳定完成某项工作，再针对那个具体问题添加最小约束。

## v2 成功标准

1. **LLM 是否能持续记住“这些人是谁”。**
2. **人物之间的关系是否能随着剧情自然变化。**
3. **人物经历几十回合以后，仍然像同一个人，并且能发生合理成长。**
4. **故事是否能在章节主题约束下自由发展，同时保持长期剧情连续性。**
